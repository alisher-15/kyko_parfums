# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Kyko is a perfume marketplace for retail and wholesale buyers. The backend is FastAPI + SQLAlchemy 2 + Alembic + PostgreSQL 16 in `backend/`. The frontend is Next.js 16 (App Router) + React 19 + Tailwind 4 in `frontend/`, and the admin panel lives at `/admin` in the same app. The customer mobile app (iOS and Android) is Expo SDK 58 + Expo Router in `mobile/`; it uses the same public API. The README and the UI are in Russian; code and comments are in English. [README.md](README.md) is the detailed product spec (pricing rules, POS, returns, warehouse). Read it before you change business logic.

## Commands

Backend (run from `backend/`; needs a local PostgreSQL with DBs `kyko` and `kyko_test`, owner `kyko`/`kyko`):

```bash
pip install -r requirements-dev.txt
cp .env.example .env
python -m app.cli migrate                # alembic upgrade + schema_compat check (use this, not bare alembic)
python -m app.cli create-admin admin@example.com admin12345
python -m app.cli seed-demo              # demo catalog + retail/wholesale/bulk@example.com, password123
uvicorn app.main:app --reload            # http://localhost:8000, Swagger at /docs

pytest                                   # all tests
pytest tests/test_orders.py::test_name   # single test
ruff check . && ruff format --check .
```

Other CLI subcommands: `import-catalog <file> [--dry-run]`, `template <file>`, `bootstrap` (admin/demo data from the ADMIN_EMAIL / ADMIN_PASSWORD / SEED_DEMO env vars; used on deploy).

Product photos: `python scripts/normalize_photos.py ../frontend/public/bottles [--dry-run]` makes every bottle photo a 600×600 white square with the bottle at the same scale. Run it after adding photos; processed files are marked and skipped next time. Admin uploads get the same processing (`app/services/images.py`, `kind=product`; banners and logos use `kind=original`) and go to Cloudflare R2 when the five `R2_*` env vars are set, otherwise to `media_dir` (`app/services/storage.py`; on Render free that disk is wiped on deploy). `python -m app.cli photos-to-r2` moves the bottle photos to R2 too (`services/bottles.py`: upload under `bottles/`, relink `/bottles/…` in products and variants), and with R2 set the importer reads `/bottles/…` as the bucket's copy (`bottles.bucket_url`).

Frontend (run from `frontend/`):

```bash
npm run dev                  # http://localhost:3000; /api and /media are proxied to BACKEND_URL (default :8000)
npm run lint && npm run typecheck && npm run build   # typecheck = next typegen + tsc (PageProps/LayoutProps are generated)
```

Mobile app (run from `mobile/`; see [mobile/README.md](mobile/README.md)):

```bash
npx expo start                                  # Expo Go on a phone; the live shop by default
EXPO_PUBLIC_SITE_URL=http://localhost:3000 npx expo start --web   # against a local site
npm run typecheck && npm run lint && npm run format:check
npx expo export --platform ios --platform android                # the native bundles build
```

Add packages with `npx expo install` (SDK-matched versions; `EXPO_OFFLINE=1` when api.expo.dev is unreachable). [mobile/AGENTS.md](mobile/AGENTS.md): Expo changes every SDK, so check the installed package's types and source rather than memory.

Browser tests (run from `e2e/`; Playwright starts the API on a wiped `kyko_e2e` database with demo data and `next start` on the existing frontend build):

```bash
npm ci && npx playwright install chromium
PYTHON=../backend/.venv/bin/python npx playwright test          # all 54 scenarios, ~2.5 min
npx playwright test tests/warehouse.spec.ts                      # one file
```

Tests share one database and run one at a time, so each test creates the users and barcodes it changes (`newCustomer`, `randomEan`) and tops up the stock it sells (`ensureStock`); don't rely on demo data staying as seeded. Any JS error in the browser fails the test (`tests/support.ts`). The camera tests use a generated Y4M video of `CAMERA_CODES` as Chromium's fake webcam.

Full stack: `docker compose up -d --build`.

## Architecture

**Single origin.** The browser only talks to Next.js. `next.config.ts` rewrites `/api/*` and `/media/*` to FastAPI. Rewrites are resolved at build time, so `BACKEND_URL` must be set during `next build`. Pages are client-rendered because prices depend on the viewer's role. `src/lib/api.ts` is the API client (JWT in localStorage, automatic refresh), and `src/lib/cart.tsx` keeps the cart in localStorage.

**Deploy.** There are two packaging modes:
- `docker-compose.yml` uses the separate `backend/` and `frontend/` images.
- The root `Dockerfile` plus `deploy/start.sh` is an all-in-one image for Render (`render.yaml`): migrate → bootstrap → uvicorn on 127.0.0.1:8000 → Next standalone server on `$PORT`.
- `deploy/vps/` runs the same all-in-one image on a VPS in Kazakhstan with PostgreSQL and Caddy (HTTPS), plus `backup.sh`; its README is the runbook (first start, filling the shop from Excel, updates, backups).

**Pricing** (`app/pricing.py`, pure functions). There are three tiers: retail, wholesale and bulk. The customer's role caps the best tier they can get. The tier is chosen by the thresholds in the `pricing_settings` row, in `order_total` mode (one tier for the whole order) or `item_quantity` mode (a tier per line). A missing wholesale or bulk price falls back to the tier above it. Business rule: the wholesale level is decided by the role, not by the order size, so in production both thresholds are 0 (the threshold modes stay available in «Настройки»). Wholesale customers additionally see the bulk price as a teaser (`next_tier_price`, `teaser_tier`), switchable by `pricing_settings.show_next_tier`; upgrade requests always target the next role (`next_role`). The server always computes prices (`POST /api/cart/quote`, `POST /api/orders`), and order items store a snapshot of price, tier, cost and product. Retail users and guests must never see wholesale prices in API responses; see `visible_tiers`.

**Markups** (`services/markups.py`). Each variant remembers its markup on the cost for every price level (`retail_markup` / `wholesale_markup` / `bulk_markup`, percent = (price / cost − 1) × 100) whenever its prices or cost are set by hand: the importer, variant create/edit (`markups.remember`). A receipt moving the average cost leaves them alone. They are what a supplier's new cost will be priced by. The products list's `price_check` filter (`below_cost`, `markup_down`, `markup_up`: actual vs remembered markup, ±`MARKUP_DRIFT` points) finds volumes to look at.

**Price history** (`services/price_history.py`, table `price_changes`). A `before_flush` hook writes every change of a variant's `cost_price` and three prices (the columns have `active_history=True`), so no write path can skip it; a new variant's first prices are not changes. Code that changes prices calls `price_history.label(db, source, user)` first («Админка», «Импорт Excel», «Прайс Канат», «Приёмка №12»); unlabelled changes say «Изменение». Shown in the product card (`GET /admin/products/{id}/price-history`).

**Suppliers** (`services/suppliers.py`, `services/price_lists.py`, `routers/admin/suppliers.py`, «Поставщики» in the admin panel). Two suppliers seeded by migration 0017: Канат (`is_main`, 1С format `usd_1c`: «Номенклатура» + «ОПТ,ЦЕНА» in tenge) and Эрик (`barcode_kzt`: «ШТРИХ - КОД» + «ОПТ»). An uploaded price list is matched line by line: a remembered link (`supplier_links`, by `price_lists.line_key`; a link without a variant = «не наш товар»), else the barcode (UPC-A/EAN-13 candidates). Matched prices become `supplier_prices`. A variant's cost is the main supplier's price, else the lowest other one; until the main supplier's first list, other lists only store their prices (`waiting_for_main`). When a list changes a variant's cost, its prices become `cost × (1 + markup)` rounded up to 100 ₸, to 10 ₸ under 5 000 ₸ (`suppliers.price_from_cost`) but **never lower than the current price** (`raised`); the cost itself follows the list both ways. A variant with no markups (no cost before) remembers the markups of its prices instead. A cost that more than doubles or halves, or a first cost above the retail price or under a fifth of it (`suppliers.odd_cost`), is not applied: the supplier's price is stored, the report lists the line in `suspicious`; `prices_not_raised` counts volumes whose prices could not follow a higher cost. Prices written as text («12 500 ₸», «15.000») are read (`price_lists._number_text`), and lines whose price cell can't be read are listed in `unreadable`, never skipped silently. Эрик's «ПРИМ» TEST line is the tester of the volume its (bottle's) barcode names, never the bottle. `POST /admin/suppliers/{id}/price-list` checks by default (`dry_run=true`) and writes with `dry_run=false`. Links can be exported/imported in Excel.

**Promotions** (`services/promotions.py`, `routers/admin/promotions.py`). A promotion is a home page banner with an optional percent off the retail price. Banners are 3:2 cards in a sideways row at the top of the home page (`HomePromotions`, a `Rail`: two and a bit on phones, four on computers, Kaspi-style), so one 1200×800 picture fits phones and computers alike. With `image_only` (a finished banner whose text is on the picture) the home page shows the picture whole instead of writing the title, dates and discount over it. It runs from `starts_on` to `ends_on` inclusive in the shop's time zone (`settings.timezone`, computed by the database), for the whole catalog or the listed brands and products. The buyer pays the lower of the tier price and the promotion price (`pricing.deal_price`, rounded to whole units), so retail buyers and guests get it and wholesale buyers only when it beats their price; promotions don't add up, and at the till the cashier's discount doesn't add to a promotion either (the better one wins). Load deals with `promotions.deals_for` / `deals_for_variants` and pass them into `QuoteItem`/`variant_public`; catalog SQL uses `promotions.price_expr` with the `promotions.discounts()` subquery outer-joined by product (the discounts are worked out once per query, never per volume), and it must stay in step with `pricing.deal_price`; `/products` joins the per-product price only when it sorts by price and works out the prices of the page's products otherwise, so the home page's many small lists stay cheap. Order lines snapshot `list_price`, `discount_percent` and `promotion_title`. There is no home page block of products on promotion: the banners lead to them. **Home page** (`app/home-sections.tsx`; the app's `components/home.tsx` has the same blocks): search, banners, a trust row, «С чего начнём?» (genders, testers, «Ниша и люкс», other sections), «Хиты продаж» (`sort=popular`: units sold in `POPULAR_DAYS`, not cancelled, `sold` on each item; «Купили N раз» from 3), «Тестеры» (`tester=true`; each list item's `tester` offer is the tester with the biggest saving on its bottle at the viewer's prices), «Выбор Kyko» (`products.new_at`, set by the «Выбор Kyko» checkbox, formerly «Новинка»; `sort=new` puts marked products first; no block while none are marked), «Подарок по бюджету» (price filters), advice in WhatsApp, «Вы смотрели» (ids kept on the device, `GET /products?id=…`), the top brands in one line, wholesale. **Top brands:** `brands.is_top` (migration 0023) puts a brand in that line and in «Ниша и люкс» (`top=true`); the column's default marks a new brand whose name is a top house (`app/top_brands.py`, `key()` folds «By Kilian» / «Parfums de Marly» / «Hermès»), whatever creates it, and the owner ticks it in «Бренды». A floating WhatsApp button is on every shop page and screen (`components/WhatsAppButton.tsx`, `mobile/src/components/whatsapp-button.tsx`): orders, payment and delivery are agreed in WhatsApp. The shop's name is «Kyko» everywhere (not «Kyko Parfum»).

**Banners and stories** (`services/creatives.py`, `routers/admin/creatives.py`, «Баннеры и сторис» and «Сделать по шаблону» in the promotion form, `CreativeMaker` on the site and `components/admin/creative-maker.tsx` in the app). Pillow draws a template, no AI and nothing paid: a banner 1200×800 or a story 1080×1920, a dark/light/gold theme, the title in the shop's serif, a subtitle, a gold badge and a note, and up to three products' real photos (trimmed to the bottle with `images.object_box`; multiplied into the light themes, on a white stage on the dark one). `POST /admin/creatives/render` returns a data URL preview, or with `save=true` stores the JPEG (`storage.save`, `creatives/…`) for a promotion's banner (`image_only`). The fonts are in `backend/app/assets/fonts` (SIL OFL); Manrope has no ₸, so `_runs` draws such characters with the serif.

**Dollar rate** (`services/rates.py`, `routers/admin/currency.py`, `frontend/src/lib/currency.tsx`). Prices are stored and charged in tenge; the ₸ / $ switch only converts them for viewing (storefront and cart; orders, the account and the admin panel stay in tenge). One `exchange_rates` row keeps the rate read from mig.kz (`settings.rate_source_url`, empty = never read; the e2e backend runs with it empty), and an `adjustment` of ±50 ₸ added to it; the effective rate is mig.kz + adjustment. A `manual_rate` only stands in while mig.kz has never answered: the first good read clears it, and the admin can't set one once a mig.kz rate exists. The public `GET /api/currency` refreshes a stale rate on demand (3 h, 15 min after a failure, one request at a time) and keeps the last good rate on any failure, including a >15% jump; it returns only the effective rate. The parser (`rates.parse_usd_rate`) reads only the mig.kz row "buy USD sell" and refuses any other layout; don't loosen it into a guess (a looser one took the EUR rate for the dollar). Its fixture in `tests/test_currency.py` is the real page. Format prices on the storefront with `useCurrency().money`, not the plain `money()` from `format.ts`.

**Import / export** (`services/importer.py`, «Импорт Excel» in the admin panel). The importer matches products by (brand, name, type), with the site's values read the same way as a file cell (`_text`, `normalize_type`), and variants by (volume, tester); empty cells never overwrite. `build_export` writes the catalog in the import columns without stock (receipts and stock counts own it), with the cost next to the three prices and each supplier's price before them («Цена Канат», `supplier_columns`; the importer skips those columns); `GET /admin/products/export` takes the products list's filters (`product_filters`, shared with `GET /admin/products`), and with `no_barcode` writes only the volumes without a barcode, and an exported file imported back must change nothing (`test_export_imports_back_unchanged`). Files built from supplier price lists should take product names from an export, or they create duplicates.

**Testers.** A tester is a `ProductVariant` with `is_tester=True`, next to the bottle of the same volume (one of each per product and volume): its own three prices (same pricing rules), stock, SKU and barcodes; it uses the product's photos. `order_items.is_tester` keeps it in the order snapshot. Name volumes with `models.volume_label` ("100 мл, тестер"; `volumeLabel` in `frontend/src/lib/format.ts` is the same), never with a bare `f"{volume_ml} мл"`. The product page picks «Товар» or «Тестер», then the volume. The importer reads testers from a «Тестер» column, or from the word tester/тестер in the name, volume or type, which it strips from the name.

**Stock.** Every stock change must go through `services/stock.move_stock` (or `set_stock`), which writes the `stock_movements` journal. The caller locks the rows with `lock_variants` (SELECT … FOR UPDATE) and commits. Stock is deducted when an order is placed and returned on cancel, edit or return. Stock may go below zero only through online checkout and stock counts (`allow_backorder=True`): customers can order what the shop doesn't have (a backorder, `order_items.backordered` records the missing units), and the minus is what they are owed; receipts fill it first, the till never sells into it. Most of the catalog is sold before it is bought, so a minus is ordinary and no edit may erase it: adding stock never fails even when the result is still below zero (a cancelled or cut backorder); cutting an order line cuts its `backordered` too; `PATCH /admin/variants/{id}` changes stock only when `stock` differs from the current one, refuses a stale form with 409 when `stock_expected` (the stock the form was opened with) no longer matches, and the site and app send `stock` only when the owner changed it, so a price edit never touches stock; an Excel import locks the volumes and never replaces a minus (the row is reported). Stock counts set stock = counted − units in orders not shipped yet (`services/warehouse.reserved`). Receipts (`services/warehouse.py`) update `cost_price` by a moving average, but only for variants no supplier has a price for: the price lists own the others' cost. A new receipt line's purchase price comes from the price list of the receipt's supplier (the main supplier's when the receipt names none; `_purchase_price`), else the last receipt or the cost. Stock counts set counted variants to the counted quantity. Barcodes live in `variant_barcodes`, and `services/barcodes.py` normalizes them (UPC-A = EAN-13 with a leading 0). Stock state is admin data: customer-facing responses (catalog, cart quote, the customer's orders) say nothing about stock except `stock` when 1–5 units are left ("Осталось мало", `app/availability.low_stock`), for every role; in stock / out / backordered are shown in the admin panel only.

**Orders** (`services/orders.py`). There are two channels (`OrderChannel`): `online` (placed on the site) and `store` (entered by an admin at `/admin/pos`). Online orders may come from guests (`user_id` NULL, retail prices, a whole phone number, `throttle.guest_orders` / `guest_orders_per_phone`); a guest sees and cancels the order at `/orders/{id}?key=…`, where the key is `orders.guest_key` (an HMAC of the id with `jwt_secret`, never stored), sent to `/api/orders/guest/{id}` in the `X-Order-Key` header so it stays out of access logs; `orders.customer_link` gives the right link for emails. A checkout or till sale may carry a `request_key` (unique `orders.request_key`, migration 0024) that the site and app make per attempt (`requestKey` in `lib/api.ts`): sending it again returns the order already placed, so a retry after a lost answer never places or deducts twice; a key never opens another account's order (409). The till also sends `expected_total`, the sum on its button, and the sale is refused (409) when the receipt came to another total; the till disables «Провести» until the quote of the receipt as it is now has come back. A request that gets 401 and whose refresh fails is retried as a guest only when it is a GET and the server really ended the session; a write (an order above all) fails with «Вход истёк» instead of becoming a guest's at retail prices, and the checkout keeps what was typed (`sessionStorage` on the site, the screen's draft in the app) and says why. Store sales are created as delivered, with an optional customer and a per-line discount capped by `max_store_discount_percent`; the store quote carries each line's `cost_price`, which the till shows with the margin behind «Показать себестоимость». Status flow: new → processing → shipped → delivered; an order can be cancelled before delivery. Before delivery an order can be edited (lines removed or reduced). After delivery it gets partial returns, where each line goes back to stock or is written off. Every change is added to the order history, which the customer also sees. Dashboard revenue and margin count delivered orders only (net of returns); orders not handed over yet are shown separately as in progress.

**Telegram** (`services/telegram.py`, `routers/admin/telegram.py`). New online orders (not store sales) are sent to every `telegram_recipients` chat by the bot in `TELEGRAM_BOT_TOKEN`, as a FastAPI background task after the checkout response, so a Telegram failure never breaks checkout. Recipients are chats, not phone numbers: the admin panel hands out a start link with a signed 24 h code (HMAC with `jwt_secret`), and `/admin/telegram/check` reads `getUpdates` and adds the chats that sent `/start <code>`. No webhook and nothing on a timer. The token is in the request URL only; never log it or put it in an error. Tests replace `telegram.call` with a fake.

**Email, errors, monitoring** (`services/email.py`, `routers/meta.py`). With `SMTP_HOST` set, password resets and customer emails go out: «order placed» after an online checkout and a note when an admin moves an online order to processing/shipped/delivered/cancelled, to the order's contact email (`email.recipient`), as background tasks. Without SMTP nothing is sent; only `EMAIL_LOG_BODY=true` (dev, the e2e backend) writes the email text, reset links included, to the log, never on a live site. `SENTRY_DSN` turns Sentry on (no request bodies, no PII); browser errors reach it through `POST /api/client-errors` (`components/ErrorReporter.tsx`, throttled 60/min overall). `/api/health` runs `SELECT 1` and answers 503 when the database is down, for Render and an uptime monitor. `next.config.ts` sends a Content-Security-Policy (scripts, styles, fonts, API calls: same origin; images: any https); a new external script needs its origin added there. Alembic's `env.py` keeps existing loggers, so tests can read the app's logs with `caplog`.

**SEO and analytics** (`src/lib/site.ts`, `app/products/[id]/page.tsx`, `app/sitemap.ts`, `app/robots.ts`, `components/Analytics.tsx`). Pages stay client-rendered, but the product page's `generateMetadata` fetches the product as a guest (`publicProduct`, straight from `BACKEND_URL`, cached per render) for the title, description, canonical URL, link preview and a schema.org `Product` JSON-LD with retail prices. A page's `openGraph` replaces the layout's whole, so spread `SITE_OPEN_GRAPH` into it; `public/og.png` is the preview of pages and products without a photo. `sitemap.xml` (active products with an active volume, `GET /api/sitemap`) and `robots.txt` are made per request (`force-dynamic`: the API isn't there at build time). Absolute URLs use `SITE_URL`, else `RENDER_EXTERNAL_URL`; static pages are built with it, so the Dockerfiles pass both as build args. Yandex Metrica (`NEXT_PUBLIC_YM_ID`) and GA4 (`NEXT_PUBLIC_GA_ID`) are built in when set: a page view per pathname change, never on `/admin`, `/account`, `/checkout`, `/orders` (guest links), `/reset-password`; the CSP adds their hosts only when the ids are set.

**Catalog sections** (`services/categories.py`, `routers/admin/categories.py`, migration 0022). `categories` is a tree up to `MAX_DEPTH` 3 (section → group → subgroup), names unique among siblings, ordered by `position`; a section's `kind` (perfume/cosmetics) is inherited by its groups and hides the perfume fields in the product form. `products.category_id` places a product (new products default to the first perfume section); a category filter (`category_id` on `/products`, `/filters`, the admin list where 0 = not placed) covers the whole subtree. The public `GET /api/categories` lists only nodes with active products, each with `image_url` (the admin's tile picture, else a product photo, `tile_images`); the home page's «С чего начнём?» shows the sections other than perfume, and its «Все категории» opens `/categories` with every section as a card, then step by step as on Kaspi (`categoryHref` / the app's `openCategory`: a node with groups opens them at `/categories?parent=`, with «Все товары» first; a leaf opens its products) (in the app `app/categories.tsx`, with the tree helpers in `mobile/src/lib/categories.ts` mirroring `frontend/src/lib/categories.ts`). `product.category` stays the olfactory group string: installed apps read it, so the section is `category_id` / `category_path`. The importer's «Раздел» column takes a path or a unique name (`categories.find`). A node can be deleted only when it has no products and no children.

**Search** (`services/search.py`, migration 0018). The database folds names to how they sound in Latin letters (`search_fold`, a plpgsql function): `brands.search_text` and `products.search_text` (name, type, `search_names`) are generated columns, so every write path keeps them right; "шанель" and "Chanel" are both `shanel`. `product_name_match` (storefront, admin list, export, till) wants every query word in brand/name/type/other names as typed (ILIKE) or as it sounds from a word start, and tries the English layout of a Cyrillic word. Only the storefront list falls back to `product_similarity` (pg_trgm `word_similarity`, average over words ≥ `SIMILAR`) when nothing matches, and says so (`similar`). Changing `search_fold` needs a migration that redefines it and re-creates the generated columns.

**Legal pages** (`app/offer`, `app/privacy`, `lib/legal.ts`). The offer and the privacy policy are templates: the seller's details and `DATA_STORAGE` come from `lib/legal.ts`, and an empty one shows as a highlighted gap (`components/LegalPage.tsx`). Checkout and registration can't be sent without the `<Consent>` checkbox (personal data law of Kazakhstan); e2e flows tick it with `getByLabel(/согласие на обработку/)`. When the privacy policy's facts change (a new processor, analytics, the hosting), update the page.

**Routers.** `routers/{auth,catalog,orders}.py` are public or customer-facing. `routers/admin/*` are staff only (`permissions.require_staff`), and `routers/admin/__init__.py` says whose each router is: `allow()` alone is the owner's (`admin`), `allow(Area.orders)` adds the roles with that area, `reading=` grants GET only. Roles and areas are in `app/permissions.py` (`cashier`: till + orders; `warehouse`: stock + orders), mirrored for the menu in `frontend/src/lib/staff.ts` and `mobile/src/lib/staff.ts`; change all three together. A route that needs the user takes `Depends(require_staff)`; owner-only data in a shared response (the cost at the till) is blanked for the others. Staff are retail buyers on the storefront. The Pydantic schemas are in `app/schemas/`.

**Mobile app** (`mobile/`). A client of the API with no backend code of its own: the shop uses the public routers (`routers/{auth,catalog,orders}.py`), and staff get the whole admin panel too: an «Админка» tab shown to `STAFF` roles only (`src/lib/staff.ts`, the same areas as `frontend/src/lib/staff.ts`; change all three together), with a screen per admin section in `src/app/admin/` calling the same `/admin/*` endpoints as the website (types in `src/lib/admin-types.ts`, mirrored from `frontend/src/lib/types.ts`). Barcodes are scanned with `expo-camera` (`components/admin/scan.tsx`), photos come from `expo-image-picker` and spreadsheets from `expo-document-picker` (`lib/files.ts`, multipart through `api(path, {form})`), and downloaded files go to the share sheet (`saveAndShare`). The app follows the website: when a storefront or admin screen, flow, text or API field changes on the website, make the same change in the app in the same PR (its screen in `mobile/src/app/`, the types in `src/lib/types.ts` / `admin-types.ts`), so the two never drift. The app calls `${EXPO_PUBLIC_SITE_URL}/api` (default: the shop's VPS at its temporary `https://89-126-205-132.sslip.io` until a domain is bought; store builds must set the final domain in `eas.json`) through the Next.js proxy, and resolves relative photo paths (`/bottles/…`, `/media/…`) against the same site (`src/lib/config.ts`). `src/lib/types.ts` and `format.ts` mirror `frontend/src/lib/` for the customer-facing types: when a public schema or a label changes, update both. Tokens live in the Keychain/Keystore (`expo-secure-store`; localStorage in the web build) and refresh like the website's; cart, favorites and the ₸/$ choice are in AsyncStorage. Prices come from the server only (`/cart/quote`, `/products`); `lib/auth.tsx` resets the React Query cache whenever the user or role changes, so no cached price outlives a login. Native apps send no `Origin`, so CORS doesn't apply to them; the web build (`expo start --web`, port 8081) needs its origin in `CORS_ORIGINS`. An API change the app uses (public or admin) must stay backward compatible: installed app versions keep calling the old shape until users update.

**Order notifications** (`services/push.py`, table `push_tokens`, `mobile/src/lib/notifications.ts`). The app registers an Expo push token per phone after the customer allows notifications (`POST /me/push-tokens`; an existing token moves to the user signed in now) and forgets it on logout (`POST /auth/push-tokens/forget`, no session needed). When an admin moves an online order to processing/shipped/delivered/cancelled (`routers/admin/orders.update_order`, next to the email), `push.send` runs as a background task: it posts to `EXPO_PUSH_URL` (Expo's push service, empty = never; tests and the e2e backend), with `channelId: "orders"` and `data.order_id`, which the app opens on tap; tokens Expo reports `DeviceNotRegistered` are deleted. Tests replace `push.call` and `push.enabled`. `expo-notifications` has no web support: guard native-only calls with `Platform.OS !== "web"` (the web build is how the app is tested here).

**Account deletion** (`POST /api/me/delete`, «Удалить аккаунт» on the site's account page and in the app). Orders reference the user (`RESTRICT`), so deletion anonymizes the row instead of removing it: email `deleted-<id>@deleted.invalid`, personal fields and the upgrade request cleared, a random password, `is_active=False`, `token_version` bumped, reset tokens and push tokens dropped. It needs the current password and shares the login throttle. Staff accounts (`permissions.STAFF`) can't be deleted this way. When a new personal field is added to `users`, clear it there too. The privacy policy says how to delete an account; keep it in step.

**Models.** Enums are stored as VARCHAR + CHECK (`_enum()` in `models.py`), not native PG enums, so adding an enum value (e.g. a new `StockReason`) needs a migration that drops and recreates the CHECK constraint (see migrations 0003 and 0006). Money is `Decimal` internally and serialized to JSON as a number (`schemas/common.Money`). After a commit in the same session, reload objects with `.execution_options(populate_existing=True)` (see `order_load_options()`), and lock with `with_for_update(of=Model)` when the query has outer joins.

## Workflow

Work on a branch and open a PR into `main`. GitHub Actions (`.github/workflows/ci.yml`) runs the backend checks, the frontend checks, the mobile checks and the browser tests on every PR and on `main`; merge only when all four jobs are green. When a UI text or flow changes, update the matching spec in `e2e/tests/`. Render auto-deploys `main`; migrations run at container start via `python -m app.cli migrate`. Before pushing, run the same checks locally.

## Migrations: required rule

Every Alembic migration must declare a module-level `backward_compatible = True/False`: can the code from before this migration run on the schema after it? Use True for new tables, nullable or server-default columns and looser constraints. Use False for NOT NULL without a default, drops, renames and stricter constraints. `app/migrations.py` records the newest breaking revision in the `schema_compat` table, so a previous build can still start after a failed deploy. A migration without the flag won't be applied, and `tests/test_migrations.py` fails. Never rename or change `schema_compat`. Split breaking changes into two releases: first add, then tighten or drop. Name migration files `YYYYMMDD_NNNN_description.py` with sequential revision ids (`"0006"`).

## Tests

pytest runs against real PostgreSQL at `TEST_DATABASE_URL` (default `postgresql+psycopg://kyko:kyko@localhost:5432/kyko_test`), never `DATABASE_URL`. The session fixture drops the schema and rebuilds it through the real Alembic migrations, and each test truncates all tables. Helpers are in `tests/conftest.py`: the `auth(role)` fixture returns headers for a new user with that role, plus `make_user` and `login`.
