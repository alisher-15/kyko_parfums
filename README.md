# Kyko Parfum — маркетплейс парфюмерии и косметики

[![CI](https://github.com/alisher-15/kyko_parfums/actions/workflows/ci.yml/badge.svg)](https://github.com/alisher-15/kyko_parfums/actions/workflows/ci.yml)

MVP веб-платформы для розничной и оптовой продажи парфюмерии и косметики: каталог по разделам
(парфюмерия с нотами и олфактивными группами, макияж, уход), три уровня цен (розница / опт /
крупный опт), корзина и заказы без онлайн-оплаты, личный кабинет и админ-панель с импортом
каталога из Excel.

| Слой | Технологии |
|---|---|
| Backend | Python 3.11, FastAPI, SQLAlchemy 2, Alembic, PostgreSQL 16, JWT (PyJWT), bcrypt |
| Frontend | Next.js 16 (App Router, Turbopack), React 19, Tailwind CSS 4, TypeScript |
| Админка | Защищённый раздел `/admin` на том же фронтенде |
| Инфраструктура | Docker Compose (db + backend + frontend) |

## Быстрый старт (Docker)

```bash
cp .env.example .env            # задайте JWT_SECRET
docker compose up -d --build
docker compose exec backend python -m app.cli create-admin admin@example.com 'сложный-пароль'
docker compose exec backend python -m app.cli seed-demo           # демо-товары и пользователи (необязательно)
```

- Сайт: http://localhost:3000, админка: http://localhost:3000/admin
- API и Swagger: http://localhost:8000/docs

Миграции применяются автоматически при старте backend-контейнера.

## Деплой в облако (Render, бесплатный тариф)

В корне лежат `Dockerfile` (сайт и API в одном контейнере) и `render.yaml` (Blueprint:
веб-сервис + бесплатный PostgreSQL).

1. Зарегистрируйтесь на https://render.com через GitHub и дайте доступ к репозиторию.
2. **New → Blueprint** → выберите репозиторий и ветку с `render.yaml`.
3. Render спросит `ADMIN_EMAIL` и `ADMIN_PASSWORD` (не короче 8 символов): это будет ваш вход
   в админку. `JWT_SECRET` сгенерируется сам, `DATABASE_URL` подставится из базы.
4. **Apply** — первая сборка идёт ~5–10 минут. Сайт откроется по адресу вида
   `https://kyko-parfums.onrender.com`.

При первом старте применяются миграции и создаётся админ. Демо-товары и демо-аккаунты
заливаются только при `SEED_DEMO=true` и только в пустой каталог; в `render.yaml` стоит
`false`, чтобы на живом магазине их не было. При перезапусках ничего не дублируется.

Ограничения бесплатного тарифа: сервис засыпает через ~15 минут простоя, первый запрос после
сна идёт ~1 минуту; бесплатная база Render живёт ограниченный срок. Фото, загруженные через
админку, без хранилища R2 лежат на диске контейнера и пропадают при новом деплое — подключите
R2 (см. «Фото флаконов»).
Демо-аккаунты с паролем `password123` публичны — перед реальным запуском удалите их
или заблокируйте в админке.

Сайт на Render стоит собирать из ветки `main`: тогда на прод попадает только то, что смержено.

### Миграции и откат неудачного деплоя

При старте контейнер выполняет `python -m app.cli migrate`, а не голый `alembic upgrade head`.
Бывает, что новая версия уже обновила базу, но её деплой упал, и Render оставил работать
предыдущую сборку. Предыдущая сборка не знает новой ревизии базы, и голый `alembic upgrade head`
падает при каждом старте.

Поэтому каждая миграция обязана объявить `backward_compatible`: работает ли код, написанный до
неё, на схеме после неё.

- `True`: новые таблицы, колонки, которые могут быть пустыми или имеют значение по умолчанию
  (`server_default`), ослабленные ограничения.
- `False`: колонка NOT NULL без значения по умолчанию, удаление или переименование, более
  строгие ограничения.

Флаг говорит только о схеме: он страхует упавший деплой, когда новый код ещё ничего не записал.
Откатывать сайт на старую сборку после того, как новая поработала, нужно осторожно: новая могла
записать данные, которых старая не знает (например, новые причины движения склада).

После каждого прогона Alembic база запоминает в таблице `schema_compat`, код какой ревизии она
требует как минимум. Если база новее кода, `migrate` запускает приложение, только когда код не
старше этого минимума. Иначе контейнер не стартует и пишет в лог, какую версию выкатить.
Миграция без флага не применится, а тесты упадут.

Ломающие изменения лучше делать в два релиза: сначала добавить (колонку, которая может быть
пустой, или значение по умолчанию), потом, отдельной миграцией, ужесточить или удалить.

## Локальная разработка

Нужны Python 3.11+, Node.js 20.9+ и PostgreSQL.

```bash
# БД
createuser -s kyko && createdb -O kyko kyko && createdb -O kyko kyko_test

# Backend (http://localhost:8000)
cd backend
python -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env
alembic upgrade head
python -m app.cli create-admin admin@example.com admin12345
python -m app.cli seed-demo
uvicorn app.main:app --reload

# Frontend (http://localhost:3000) — /api и /media проксируются на backend
cd frontend
npm install
npm run dev
```

Демо-аккаунты после `seed-demo` (пароль `password123`):

| Email | Роль |
|---|---|
| retail@example.com | Розница |
| wholesale@example.com | Опт |
| bulk@example.com | Крупный опт |

Оптовая цена зависит только от роли покупателя: пороги по сумме заказа выключены (равны 0).

## Разделы каталога: парфюмерия и косметика

Товары лежат в дереве категорий, которое админ правит сам (админка → «Категории»):

- **разделы** — меню сайта: «Парфюмерия», «Макияж», «Уход за лицом», «Уход за телом», «Уход за
  волосами», «Аксессуары» (стартовый набор по образцу Mon Amie, его можно менять);
- **группы** внутри раздела («Макияж» → «Губы», «Глаза»…) и **виды** в группе («Губы» →
  «Помада»). Уровней не больше трёх;
- добавить, переименовать, перенести в другой раздел, поменять порядок (↑ ↓), удалить.
  Удалить можно только пустую категорию: сначала перенесите товары и удалите группы внутри.
  Названия не повторяются внутри одного раздела, в разных — могут («Маски» есть и в уходе за
  лицом, и в уходе за волосами).

**Тип раздела** — «Парфюмерия» или «Косметика» — задаёт поля товара. У парфюмерии есть
концентрация (EDP, EDT…), олфактивная группа, стойкость и ноты; у косметики этих полей в карточке
товара в админке нет, и на витрине они не показываются. Группы берут тип своего раздела, а
перенос в другой раздел меняет его вместе со всеми группами внутри. Все товары, что были в
магазине до разделов, попали в «Парфюмерию».

На сайте:

- на компьютере под логотипом строка разделов, в которых есть товары; у каждого выпадающее
  меню с группами, у парфюмерии в нём «Женские / Мужские / Унисекс». На телефоне то же в меню ☰.
  Разделы и группы без товаров не показываются;
- страница раздела (`/catalog?category_id=…`) показывает товары всех его групп, группы —
  кнопками над списком, хлебные крошки и фильтры только по тому, что в разделе есть (бренды,
  цены, пол, концентрация);
- в карточке товара хлебные крошки «Каталог / Макияж / Губы / …»; в плитке каталога у
  парфюма пол и олфактивная группа, у косметики — её группа.

В админке у товара поле «Категория» (обязательное), в списке товаров — фильтр и колонка
«Категория». Импорт: колонка «Раздел» (см. «Импорт каталога из Excel»).

## Роли и цены

| Роль | Что видит | Какую цену может получить |
|---|---|---|
| Гость | Каталог, розничные цены | Розничную (для заказа нужен вход) |
| Розница (`retail`) | Розничные цены | Розничную |
| Опт (`wholesale`) | Розница + опт | Оптовую |
| Крупный опт (`bulk_wholesale`) | Все три цены | Крупнооптовую |
| Админ (`admin`) | Всё + админ-панель | — |

Роли опт/крупный опт назначает администратор вручную. Покупатель отправляет заявку из
личного кабинета: розница просит опт (указывает компанию и телефон), опт просит крупный опт
(с комментарием об объёмах). Заявки с комментарием подсвечиваются в «Пользователях». Когда
админ повышает роль, заявка закрывается, а новые цены действуют сразу, даже для уже выданных
токенов.

**Кто какие цены видит.** Розничные покупатели и гости оптовых цен не видят никогда. Иначе
покупатели ваших оптовиков-перепродавцов увидели бы их закупочную цену. Вместо цен в каталоге
и на карточке товара показывается блок «Для магазинов и салонов» с кнопкой заявки. Оптовикам
показывается «ваша следующая цена» — цена крупного опта с условиями и кнопкой «Запросить
крупный опт», а в корзине — сколько стоил бы заказ на крупном опте. Этот тизер включается и
выключается в «Настройках», там же пишутся условия перехода. Колонка цен крупного опта
по-прежнему видна только крупным оптовикам.

У каждого объёма товара (30/50/100 мл…) свои остаток и три цены. Если оптовая или
крупнооптовая цена не заполнена, берётся цена уровнем выше (крупный опт → опт → розница).

**Тестеры.** Часть ароматов продаётся и тестерами: тот же парфюм в простой упаковке. Тестер —
отдельный вариант товара рядом с обычным флаконом того же объёма. У него свои три цены
(розница / опт / крупный опт, по тем же правилам, что и у флакона), свой остаток, артикул и
штрихкоды, а фото — те же, что у товара. На карточке товара покупатель выбирает «Товар» или
«Тестер», а ниже — объём, у каждого объёма своя цена. При переключении выбранный объём
сохраняется, если он есть в обоих. В корзине, заказе, кассе, приёмке и
инвентаризации такой объём подписан «100 мл, тестер». В админке это галочка «Тестер» у объёма,
а в импорте — колонка «Тестер» или слово «tester» / «тестер» в названии (см. «Импорт каталога
из Excel»). Цена «от» в каталоге учитывает и тестеры. EDP, EDT и экстракт остаются отдельными
товарами: у них разные флаконы и фото, а выбрать их можно фильтром «Тип» в каталоге.

**Акции** (админка → «Акции»). Акция — это баннер на главной и, если указан процент, скидка:
- действует с даты начала по дату конца включительно, по времени магазина (`TIMEZONE`,
  Алматы); без дат — пока её не выключат;
- охватывает весь каталог, бренды целиком или отдельные товары (что-то одно), все их объёмы
  и тестеры. Акция на товар «Bvlgari Tygar» — это «Отдельные товары», а не бренд Bvlgari;
- скидка считается от розничной цены и округляется до целых. Розница и гости платят цену
  по акции, оптовики — меньшую из своей цены и акционной;
- две акции на один товар не суммируются, действует большая скидка. На кассе скидка кассира
  тоже не прибавляется к акции: покупатель получает лучшую из двух;
- на сайте: баннеры идущих акций на главной (ведут на подборку `/catalog?promotion_id=…`;
  сменяются сами каждые 5 секунд и ждут, пока покупатель держит баннер пальцем или курсором),
  блок «Акции» с товарами со скидкой, бейдж «−15%» на карточках, «Акция −15%» у цены,
  фильтр «Акции» в каталоге. Корзина, заказ и касса считают цену сами;
- в строке заказа запоминаются цена до скидки, процент и название акции, поэтому после
  окончания или удаления акции заказ не меняется;
- без процента акция — только баннер, цены не меняются.
- баннер одной формы на телефоне и на компьютере, 8:3: одна картинка 2400×900 заполняет его
  везде без обрезки и полос, меняется только размер (на телефоне баннер невысокий, поэтому
  сайт пишет на нём только скидку, даты и название, без описания);
- галочка «Готовый баннер: текст уже на картинке» — для макетов, где название и условия уже
  нарисованы: сайт показывает картинку целиком и не пишет поверх неё свои название, даты и
  скидку; если пропорции картинки не 8:3, свободное место заполняет её размытая копия. Без
  галочки сайт пишет текст поверх картинки (слева внизу), картинка заполняет баннер.

**Новинки.** Блок «Новые поступления» на главной показывает товары, отмеченные галочкой
«Новинка» в карточке товара в админке, сначала отмеченные последними. Пока не отмечено ничего,
там последние добавленные товары. На карточках таких товаров бейдж «Новинка», в каталоге и в
списке товаров админки есть фильтр «Новинки».

**Что покупатель знает об остатках.** Только «Осталось мало: 2 шт.», когда в наличии от 1 до
5 штук: это помогает продавать. Больше витрина о наличии не говорит ничего, ни гостям, ни
рознице, ни оптовикам: ни «в наличии», ни «нет в наличии», ни «под заказ», нет и фильтра
«в наличии». Точный остаток — коммерческие данные, а заказать можно и то, чего нет (см. «Товар
под заказ»). Всё про наличие видно только в админке. Правило в `backend/app/availability.py`, и
API тоже ничего лишнего не отдаёт: ни в каталоге, ни в корзине, ни в заказе покупателя.

### Цены в долларах

В шапке сайта кнопка **₸ / $**: покупатель может смотреть цены в долларах. Выбор запоминается в
браузере. Доллары показываются на витрине (главная, каталог, карточка товара) и в корзине с
оформлением; заказы, личный кабинет и админка всегда в тенге. Это только пересчёт для просмотра:
заказ оформляется и оплачивается в тенге, и в корзине под итогом в долларах написано
«Оплата в тенге: … · курс 1 $ = … ₸».

Курс на сайте = курс [mig.kz](https://www.mig.kz/) (курс продажи) + поправка из админки. Курс
mig.kz запоминается; сайт читает его сам, когда покупатель заходит, если прошлое чтение было
больше 3 часов назад, и поправка прибавляется к каждому новому курсу. Если mig.kz не отвечает
или страница изменилась, остаётся последний полученный курс, а следующая попытка через 15 минут.
Курс, который отличается от прошлого больше чем на 15%, считается сбоем разбора и не
принимается. В админке, «Настройки» → «Курс доллара»:

- видно, какой курс сейчас на сайте, что показал mig.kz и когда, а также причина последней
  неудачи;
- **поправка** от −50 до +50 ₸ к курсу mig.kz (кнопки −10, −5, +5, +10). Она остаётся, пока её
  не поменяют: mig.kz показал 441,90, поправка +5 — на сайте 446,90; завтра mig.kz покажет 443 —
  на сайте будет 448;
- «Обновить сейчас» читает mig.kz сразу;
- **курс вручную** — только пока mig.kz не дал ни одного курса (например, сразу после запуска,
  если mig.kz недоступен). Первый же курс с mig.kz заменяет его, и поле пропадает. Если mig.kz
  перестал отвечать потом, остаётся последний полученный курс с поправкой.

Пока курса нет совсем (mig.kz ещё не прочитан и курса вручную нет), кнопки ₸ / $ на сайте нет.
Адрес источника задаётся `RATE_SOURCE_URL` (пусто — не читать вообще, курс только вручную).
На странице mig.kz каждая валюта — строка «покупка · код · продажа» (`439.3 USD 441.9`). Ищется
только строка с USD, берётся продажа. Числа принимаются, если продажа не ниже покупки и не выше
неё больше чем на 5%. Курс Нацбанка ниже на странице не подходит, а строки по-другому
устроенной вёрстки не угадываются: лучше отказ, чем чужое число (первая версия взяла покупку
евро). Если mig.kz поменяет вёрстку и курс перестанет находиться, админка покажет причину, а
рабочим остаётся последний курс или введённый вручную.

### Порог перехода на опт

Решение: **опт определяется ролью**, независимо от суммы заказа, поэтому пороги равны 0.
Если когда-нибудь понадобится минимальная сумма или количество для опта, это включается в
админке («Настройки») без релиза. Поддержаны два режима:

- **По сумме заказа** (`order_total`, режим по умолчанию). Уровень цены выбирается один раз
  для всего заказа: лучший доступный роли уровень, у которого сумма заказа (посчитанная по
  ценам этого уровня) не меньше порога. Пример: опт от 150 000 ₸, крупный опт от 500 000 ₸.
- **По количеству единиц** (`item_quantity`). Уровень выбирается для каждой позиции: оптовая
  цена действует, если одного объёма в заказе не меньше N штук.

Если порог не достигнут, позиция считается по рознице, и оптовик всё равно может оформить
заказ. Корзина подсказывает, сколько не хватает («добавьте ещё на 88 800 ₸» / «ещё 2 шт.»).

Цены всегда считает сервер (`POST /api/cart/quote`, `POST /api/orders`). Корзина хранится в
браузере, и при оформлении цены пересчитываются заново. В заказ записываются применённая цена,
её уровень и снимок товара, поэтому история заказов не меняется при правке каталога.

## Продажи в магазине (оффлайн) и журнал склада

Покупки в физическом магазине админ проводит в разделе **«Продажа в магазине»** (`/admin/pos`).
Экран удобен с телефона или планшета у кассы.

- Товар ищется по названию, бренду или артикулу. Сканер штрихкодов работает как клавиатура:
  сканируете код, и позиция сразу попадает в чек (точное совпадение артикула).
- Покупатель необязателен. Можно найти клиента по телефону, email или имени: тогда подставится
  его уровень цены (опт / крупный опт), а продажа попадёт в его историю заказов. Для анонимного
  покупателя можно записать имя и телефон.
- Уровень цены выбирается автоматически или вручную. Скидка задаётся на позицию или на весь
  чек, но не больше лимита из «Настроек» (по умолчанию 10%).
- Способ оплаты: наличные, карта, Kaspi / перевод, другое.
- Продажа сохраняется как заказ с каналом «Магазин» и статусом «Доставлен», остатки списываются
  сразу. Если товара на складе меньше, чем в чеке, провести продажу нельзя.
- Возврат, в том числе частичный: откройте продажу и нажмите «Оформить возврат» (см. ниже).
- В «Заказах и продажах» есть фильтр «Сайт / Магазин», на дашборде — выручка по каналам и
  продажи в магазине за сегодня. Фискальный чек система не печатает, его пробивают на кассе.

Каждое изменение остатка записывается в **журнал склада** (таблица `stock_movements`): заказ на
сайте, продажа в магазине, отмена или возврат, ручная правка в админке (с причиной, например
«приход от поставщика»), импорт Excel. Журнал виден в карточке товара в разделе
«Движение склада». В нём видно, когда, на сколько, почему и кем изменён остаток.

## Товар под заказ

Корзину можно собрать и заказ оформить независимо от наличия: то, чего нет, обычно можно
привезти за 1–2 дня. Покупатель этого не видит: кнопка всегда «В корзину», а при оформлении
сказано, что менеджер свяжется и подтвердит наличие и срок доставки.

- При оформлении остаток уходит в минус. Минус — это сколько штук должны клиентам. В позиции
  заказа запоминается, сколько не хватало (видно только в админке).
- Менеджер видит пометку «под заказ» в списке заказов, плашку в самом заказе и по каждой позиции
  подпись «на складе не хватает N шт.» или «уже на складе». На дашборде есть плитка «Нужно
  заказать у поставщика», она ведёт на товары с фильтром «Нужно заказать».
- Дальше два пути: заказать у поставщика и провести приёмку (она сначала закрывает минус) или
  через «Изменить состав» убрать то, чего не будет. Убранное возвращается на склад, покупатель
  видит изменение и причину в истории заказа. Отмена заказа тоже возвращает всё.
- Касса в магазине продаёт только то, что есть на полке и не обещано клиентам.
- То, что достать нельзя совсем, снимайте с публикации, чтобы его не заказывали.

## Изменение заказа и возвраты

**До выдачи** (статус «Новый» или «В обработке») админ может нажать «Изменить состав», уменьшить
количество или убрать позиции, например если товара нет в наличии. Снятый товар возвращается
на склад, сумма пересчитывается, цены оставшихся позиций не меняются. Покупатель видит в
кабинете тот же заказ: убранные позиции зачёркнуты, в истории указана причина. Убрать все
позиции нельзя — такой заказ отменяется целиком.

**После выдачи** (статус «Доставлен», в том числе все продажи в магазине) оформляется
возврат: какие позиции и сколько штук вернули, способ возврата денег и причина. По каждой
позиции выбирается «на склад» или «брак — списать». Сумма считается по цене, за которую товар
купили (с учётом скидки). Возвратов по заказу может быть несколько, пока не вернут всё.
Выручка на дашборде — это выданные заказы (продажи в магазине выдаются сразу) за вычетом
возвратов. Заказы, которые ещё не выданы (новые, в обработке, отправленные), могут отмениться
или измениться, поэтому показаны отдельно: «В работе, ещё не выдано».

У каждого заказа есть история (оформлен, смена статуса, изменения состава, возвраты). Её
видят и админ, и покупатель.

**Накладная.** На странице заказа в админке: «Накладная Excel» скачивает файл
`nakladnaya_<номер>.xlsx`, «Накладная PDF / печать» открывает страницу для печати (в окне печати
выберите «Сохранить как PDF»). В накладной покупатель, телефон, адрес, оплата, товары с типом
(EDP, EDT…), полом, объёмом, отметкой «тестер», количеством и ценой, итог и строки для подписей.
Убранные до отправки позиции в неё не попадают.

## Склад: сканер, приёмка, инвентаризация, сборка

**Сканер.** Подходит любой USB- или Bluetooth-сканер штрихкодов в режиме клавиатуры (HID) с Enter
после кода — так они настроены по умолчанию, драйверы не нужны. Каждое нажатие курка — одна
штука. Курсор может стоять где угодно: сайт отличает сканер от человека по скорости (сканер
печатает символы с промежутком в несколько миллисекунд) и отправляет код в сканер страницы, а
поле, куда он случайно напечатался (количество, цена, имя покупателя), возвращает как было.
Раскладка тоже не важна: при таком вводе буквы берутся по физическим клавишам, а код с кириллицей,
набранный в поле сканера, переводится в латиницу по расположению клавиш («ФИС12345» →
«ABC12345»).

На телефоне главная кнопка — «Сканировать камерой», поле ниже — для ввода кода руками (или для
Bluetooth-сканера); на компьютере наоборот. Камере нужен https. Распознавание: встроенный в
браузер детектор, где он есть (Chrome на Android), иначе ZXing (iPhone).

Камера работает по правилу «один скан — одно действие»:

1. читается только штрихкод внутри рамки, соседние коробки на полке не мешают;
2. как только код прочитан, кадр замирает, телефон вибрирует и видно «Код … прочитан · ищем
   товар…» — держать камеру дальше не нужно;
3. появляется карточка: товар, количество с кнопками −/+ и «Отменить этот скан». Больше ничего
   не считывается, пока не нажата «Следующий товар» (или тап по кадру). Сразу после этого тот
   же код игнорируется, пока не уйдёт из рамки, — коробка, оставшаяся перед камерой, не
   посчитается дважды. Несколько одинаковых коробок быстрее добавить кнопкой «+».

После скана звучит сигнал: короткий высокий — принято, длинный низкий — ошибка. Карточка
последнего скана с −/+ и отменой остаётся и под полем ввода (для ручного сканера). Незнакомый
код предлагает «Привязать к товару». Если телефон умеет, в камере есть кнопка «Фонарик».

**Штрихкоды** хранятся у объёма, их может быть несколько (разные поставщики, коробка и флакон).
У тестера свои штрихкоды: это отдельный объём.
Добавить можно в карточке товара, при импорте (колонка «Штрихкод», несколько кодов через
запятую) или прямо при приёмке: незнакомый код предлагается привязать к товару. Старые
штрихкоды, импортированные в «Артикул», тоже находятся. UPC-A (12 цифр) и EAN-13 с ведущим нулём
считаются одним кодом.

**Приёмка** (`/admin/receipts`) — приходная накладная: поставщик, № накладной, товары и
закупочные цены. Каждый скан добавляет 1 шт.; цена подставляется из прошлой приёмки. Пока
документ — черновик, остатки не меняются. «Провести» добавляет товар на склад (в журнале
причина «Приёмка» со ссылкой на документ) и пересчитывает **себестоимость** объёма по
скользящей средней: `(остаток × старая себестоимость + пришло × цена) / (остаток + пришло)`.
Если прежняя себестоимость неизвестна, берётся цена прихода. Проведённый документ не меняется.

**Инвентаризация** (`/admin/inventory`) — пересчёт полки или всего склада сканером. Видно,
сколько в системе и сколько посчитано. При проведении остатки посчитанных объёмов
пересчитываются по посчитанному (с учётом товара в заказах, см. ниже), расхождение пишется в
журнал (причина «Инвентаризация»). Не посчитанные
объёмы не меняются: товар, которого нет на полке, добавьте через поиск с количеством 0.

Товар, отложенный под заказы, которые ещё не отправлены (статусы «Новый» и «В обработке»),
лежит на полке, но уже продан. Считайте его вместе со всем остальным: «В системе» показывает
свободный остаток плюс отложенное («из них в заказах: 2»), а после проведения остаток становится
«посчитано минус отложенное». Так пересчёт не превращает обещанное клиентам в свободный товар и
не стирает минус по товарам под заказ.

**Сборка онлайн-заказа** — кнопка «Собрать заказ» у заказа в статусе «Новый» или «В обработке».
Сканируйте товары: система отмечает собранное и предупреждает о другом объёме, лишней штуке или
товаре не из заказа. Когда всё собрано — кнопка «Отметить „Отправлен“». Склад при сборке не
меняется: он списан при оформлении. Прогресс сборки сохраняется при перезагрузке вкладки.

**Касса** принимает скан сразу: товар по штрихкоду добавляется в чек.

**Маржа.** Каждая продажа запоминает себестоимость единицы на момент продажи. На дашборде:
валовая прибыль и маржа по выданным продажам с известной себестоимостью (с учётом возвратов), стоимость
склада по себестоимости и число объёмов в наличии без себестоимости. Себестоимость можно задать
и вручную в карточке товара, а при импорте — колонкой «Себестоимость».

## Импорт каталога из Excel

Файл кладётся в `data/` (папка в `.gitignore`), затем:

```bash
cd backend
python -m app.cli import-catalog ../data/catalog.xlsx --dry-run   # отчёт без записи
python -m app.cli import-catalog ../data/catalog.xlsx
python -m app.cli template ../data/template.xlsx                  # пустой шаблон
```

Или через админку: «Импорт Excel» (там же скачивается шаблон).

- Форматы: `.xlsx` и `.csv` (UTF-8 или Windows-1251, разделитель `,` `;` или табуляция).
- Строка заголовков ищется среди первых 15 строк, колонки распознаются по названию
  (рус./англ.): Бренд, Название, Раздел, Тип, Категория / Олфактивная группа, Пол, Стойкость,
  Верхние ноты, Ноты сердца, Базовые ноты, Описание, Фото, Объём, Тестер, Цена / Розница, Опт,
  Крупный опт, Остаток, Артикул, Штрихкод, Себестоимость. Нераспознанные колонки перечисляются
  в отчёте.
- «Раздел» — место в дереве категорий: путь «Макияж / Губы» или название, которое есть только у
  одной категории («Кремы»). Если такой категории нет или название встречается в нескольких
  разделах («Маски»), строка пропускается с ошибкой в отчёте. Строки без раздела — парфюмерия:
  новые товары попадают в первый раздел с типом «Парфюмерия». «Категория» в файле по-прежнему
  значит олфактивную группу: так она называется в прайсах поставщиков парфюма.
- Одна строка — один товар. Если в строке заполнены объём и розничная цена, создаётся ещё и
  вариант. Строки с одинаковыми брендом, названием и типом дают несколько объёмов одного товара.
- Тестер — строка с «да» в колонке «Тестер» (или «Товар/Тестер» со значением «тестер») либо
  со словом «tester» / «тестер» в названии, объёме или типе: «Coco Mademoiselle Tester»,
  «100 мл (тестер)», «EDP Tester». Слово убирается из названия, поэтому тестер добавляется к
  тому же товару рядом с флаконом, со своими ценами из той же строки. Отчёт показывает, сколько
  строк распознано как тестеры, — это видно уже при проверке без сохранения.
- Значения нормализуются: «Женский / жен. / women» → female, «Парфюмерная вода /
  Eau de Parfum» → EDP, цены вида «45 000 ₸» или «45,5» разбираются как числа.
- Повторный импорт идемпотентен: товары сопоставляются по (бренд, название, тип), а пустые
  ячейки не затирают уже заполненные данные. Так можно сначала залить базу из 932 позиций без
  цен, а позже догрузить цены и объёмы тем же или отдельным файлом.
- Ошибочные строки пропускаются и попадают в отчёт с номером строки Excel.

Товары без объёмов и цен видны в каталоге с пометкой «Цена по запросу». В админке для них
есть фильтр «Без цен/объёмов», а на дашборде — счётчик.

Фильтр «Без фото» в списке товаров показывает товары, у которых на витрине заглушка вместо
фото: нет ни фото товара, ни фото ни одного из его флаконов. Он складывается с поиском,
брендом и другими фильтрами, а ссылка `/admin/products?no_photo=true` открывает список сразу
с ним.

Поиск, фильтры и номер страницы списка товаров хранятся в адресе. Поэтому после карточки
товара список возвращается таким, каким был: и кнопкой «Назад» браузера, и ссылкой
«← К списку товаров» в карточке, и после удаления товара. Пункт «Товары» в меню открывает
список без фильтров.

### Фото флаконов

Фото поставщиков лежат в `frontend/public/bottles` и отдаются самим сайтом, поэтому переживают
передеплой. Флаконы на них сняты по-разному: где-то занимают весь кадр, где-то маленькие
посреди пустого фона. Скрипт приводит их к одному виду: квадрат 600×600, бутылка по центру,
её длинная сторона занимает 86 % кадра, фон белый.

```bash
cd backend
pip install -r requirements.txt
python scripts/normalize_photos.py ../frontend/public/bottles --dry-run   # отчёт без изменений
python scripts/normalize_photos.py ../frontend/public/bottles
```

- Светлый фон становится чисто белым. Чисто чёрный фон — это обычно потерянная прозрачность
  (PNG, сохранённый в JPEG): он заливается белым от краёв, тёмные детали флакона не трогаются.
- Светлый фон с градиентом (студийный серый, неровный свет) тоже становится белым: фон каждой
  строки вычисляется по левому и правому краю кадра, всё, что от него отличается, — флакон.
  Тёмный или сложный фон (стол, интерьер) и флаконы, обрезанные краем кадра, не меняются —
  скрипт перечисляет их в конце.
- Имена файлов не меняются, ссылки на фото в товарах остаются рабочими. Обработанные файлы
  помечаются, повторный запуск их пропускает. Запускайте после добавления новых фото.

**Фото из админки** («Загрузить фото» у товара и объёма) обрабатываются так же сразу при
загрузке (`app/services/images.py`): поворот по EXIF с телефона, обрезка, белый квадрат 600×600,
JPEG. Если фон неоднородный (стол, тень, интерьер), фото сохраняется без обработки и админка
пишет об этом — переснимите на белом фоне (лайтбокс). Баннеры акций и логотипы брендов не
обрезаются, только уменьшаются до 2400 px (JPEG качества 90), чтобы баннер во всю ширину был
чётким и на экранах с высокой плотностью. Файл до 15 МБ.

Баннер акции растягивается на всю ширину страницы в пропорции 8:3, поэтому картинка нужна
широкая: от 1200 px, лучше 2400×900. Маленькая картинка, например логотип из интернета, выйдет
размытой, а картинка других пропорций не заполнит баннер ровно: форма акции предупреждает и о
том, и о другом.

Где хранятся загруженные фото (`app/services/storage.py`): если заданы все пять переменных
`R2_ENDPOINT`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET`, `R2_PUBLIC_URL` —
в Cloudflare R2 (бесплатно до 10 ГБ), и они переживают деплой. Иначе — в папке `backend/media`.

Как подключить R2: Cloudflare → R2 Object Storage → Create bucket (`kyko-photos`) → Settings →
Public access → R2.dev subdomain → Allow (это `R2_PUBLIC_URL`); R2 → Manage API tokens → Create
API token с правами Object Read & Write на этот bucket (Access Key ID, Secret Access Key и
endpoint `https://<id>.r2.cloudflarestorage.com`). Все пять значений — в Render → сервис →
Environment.

## Уведомления о заказах в Telegram

О каждом новом заказе с сайта бот магазина пишет в Telegram: номер и сумма, позиции (и чего нет
в наличии), имя, телефон, адрес, комментарий и ссылка на заказ в админке. Продажи в магазине
не присылаются. Сообщение уходит в фоне после ответа покупателю: если Telegram недоступен,
заказ всё равно оформляется, а неудача пишется в лог.

Подключение, один раз:

1. В Telegram откройте @BotFather → `/newbot` → имя и адрес бота (кончается на `bot`). Он
   пришлёт токен.
2. Render → сервис → Environment → `TELEGRAM_BOT_TOKEN` = токен → Save (сайт перезапустится).
   Токен — как пароль: не пересылайте его и не коммитьте.
3. Админка → «Настройки» → «Уведомления в Telegram» → «Добавить получателя».

Получатели — это чаты, а не номера телефонов: бот не может написать человеку первым. Поэтому
админка даёт ссылку на бота (действует 24 часа, подписана `JWT_SECRET`): «Человеку» — сообщения
придут в его чат с ботом, «В группу» — бот добавится в выбранную группу, и заказы увидят все её
участники. Ссылку можно открыть самому или переслать сотруднику; после нажатия «Старт» получатель
появляется в списке сам (страница проверяет каждые несколько секунд) или по кнопке «Проверить».
Сменился менеджер или телефон — добавьте нового получателя и уберите старого; на сервере ничего
менять не нужно. «Отправить тестовое сообщение» показывает, до кого сообщение не дошло (бота
заблокировали или удалили из группы).

Бот ничего не делает по таймеру и не ставит webhook: новые «Старт» читаются `getUpdates` только
по запросу из админки. Не подключайте один и тот же бот к двум серверам (например, локальному и
боевому): они будут забирать сообщения друг у друга. Ссылка на заказ в сообщении строится из
`FRONTEND_URL` (на Render подставляется адрес сервиса; со своим доменом задайте его явно).
Код — `backend/app/services/telegram.py`, получатели — таблица `telegram_recipients`.

## Восстановление пароля

`POST /api/auth/forgot-password` отправляет письмо со ссылкой `/reset-password?token=…`
(одноразовый токен, живёт 60 минут, в БД хранится только его sha256). Если SMTP не настроен
(`SMTP_HOST` пустой), ссылка пишется в лог backend'а. Это удобно для разработки. Смена или
сброс пароля отзывает все refresh-токены пользователя.

Защита от перебора: после 10 неверных паролей подряд вход в этот аккаунт закрыт на 15 минут
(ответ 429 с `Retry-After`, даже при верном пароле). Писем для сброса — не больше 3 в час на
адрес; сверх лимита ответ тот же, письмо не уходит. Счётчики живут в памяти процесса и
сбрасываются при перезапуске.

### Схема БД

`users`, `brands`, `products`, `product_variants`, `orders`, `order_items` — как в ТЗ. Сверх ТЗ
добавлено:

- `users`: `full_name`, `phone`, `company_name`, `wholesale_requested`, `is_active`,
  `token_version` (отзыв refresh-токенов);
- `categories` — дерево разделов и групп (`parent_id`, `kind`: парфюмерия или косметика,
  `position`); `products.category_id` — где товар в дереве. Олфактивная группа — колонка
  `products.category` (в коде `olfactory_group`);
- `products`: `image_url` (главное фото), `is_active`, `new_at` (отмечен «Новинкой»);
- `exchange_rates` — курс доллара (одна строка): курс mig.kz, поправка, курс вручную (пока mig.kz
  не ответил);
- `promotions` + `promotion_brands` / `promotion_products` — акции и на что они действуют;
- `product_variants`: `sku`, `is_active`, `cost_price` (средняя себестоимость), `is_tester`,
  уникальность (товар, объём, тестер), CHECK на цены; `variant_barcodes` — штрихкоды объёма;
- `orders`: контакты и адрес доставки, `customer_role` на момент заказа, `admin_note`;
- `order_items`: `price_tier`, `cost_price` на момент продажи, снимок товара (бренд, название,
  объём, тестер ли это) и акции (`promotion_title`);
- `stock_movements` — журнал склада; `stock_receipts` / `stock_counts` (+ строки) — приёмки и
  инвентаризации;
- `pricing_settings` — режим и пороги опта;
- `password_reset_tokens`.

Остаток списывается при оформлении заказа под блокировкой строк (`SELECT … FOR UPDATE`), так
что параллельные заказы не теряют списания. Если товара не хватает, остаток уходит в минус
(товар под заказ, см. выше). При отмене заказа товар возвращается на склад.
Переходы статусов: новый → в обработке → отправлен → доставлен; отменить можно до доставки.
Покупатель сам может отменить только новый заказ.

### Браузерные тесты (Playwright)

`e2e/` проходит сайт в настоящем Chromium так, как это делают люди: 38 сценариев.

- **Витрина**: главная, каталог (поиск, фильтры, сортировка), бренды, карточка товара,
  корзина гостя.
- **Разделы**: админ добавляет группу в «Макияж» и товар косметики (без парфюмерных полей),
  сайт показывает раздел в меню, страницу группы и раздела, хлебные крошки; «Женские» у
  парфюмерии; непустую группу удалить нельзя.
- **Покупатель**: регистрация → заказ → отмена, профиль, смена пароля, заявка на опт,
  восстановление пароля по ссылке из письма.
- **Цены**: оптовые цены, тизер крупного опта, выдача роли админом, выключение тизера.
- **Тестеры**: выбор «Товар / Тестер» в карточке, цены тестера по роли, корзина и заказ с
  пометкой «тестер», галочка «Тестер» в админке.
- **Доллар**: курс в админке (поправка, курс вручную без mig.kz), кнопка ₸ / $ на витрине,
  корзина с оплатой в тенге, заказы остаются в тенге. mig.kz в тестах не читается
  (`RATE_SOURCE_URL` пуст).
- **Акции и новинки**: акция из админки — баннер на главной, скидка в карточке, корзине, заказе
  и на кассе, выключение; галочка «Новинка» ставит товар в «Новые поступления».
- **Безопасность**: заголовки, закрытая админка, редирект после входа, блокировка перебора
  паролей, загрузка только настоящих картинок, блокировка покупателя.
- **Админка**: бренд, товар и объём, импорт Excel, заказы, пользователи, настройки.
- **Склад**: штрихкоды, приёмка со средней себестоимостью, инвентаризация, сборка заказа,
  касса, возвраты и изменение заказа.
- **Сканеры**: ручной сканер (курсор в любом поле, русская раскладка) и камера. Для камеры
  тест генерирует видео со штрихкодами и подставляет его в Chromium вместо веб-камеры.
- **Телефон**: страницы витрины и админки без горизонтального скролла, а поля ввода на сенсорном
  экране не мельче 16px (иначе iPhone увеличивает страницу при нажатии на поле и не возвращает
  масштаб).

Playwright сам запускает оба сервера. Скрипт `e2e/scripts/start-backend.sh` очищает базу
`kyko_e2e` (создаёт её при необходимости), применяет миграции, создаёт админа и демо-каталог.
Базу с другим именем, в котором нет `e2e` или `test`, он очистить откажется. Фронтенд
запускается из готовой сборки. Любая ошибка JavaScript в браузере валит тест.

Локально (Linux, macOS или WSL; нужны PostgreSQL и зависимости backend):

```bash
cd frontend && npm run build
cd e2e && npm ci && npx playwright install chromium
PYTHON=../backend/.venv/bin/python npx playwright test   # ~2 минуты
npx playwright show-report                               # отчёт со скриншотами и трейсами
```

Если сервера уже запущены на :3000 и :8000, Playwright использует их и базу не очищает.

### Автотесты в GitHub Actions (CI)

`.github/workflows/ci.yml` запускает эти же проверки на каждый pull request и на каждый пуш
в `main`. Три параллельных задания:

- **Backend (ruff, pytest)**: линтер, форматирование и все тесты на PostgreSQL 16 (~2 мин);
- **Frontend (eslint, tsc, build)**: линтер, проверка типов и production-сборка (~1 мин);
- **Browser tests (Playwright)**: сборка сайта и все браузерные сценарии (~5 мин). Если тест
  упал, к прогону прикладывается архив `playwright-report` со скриншотами, трейсами и логом
  backend: скачайте его на странице прогона и откройте `npx playwright show-report`.

Результат виден в PR (зелёная галочка или красный крестик) и во вкладке **Actions**
репозитория. Чтобы красный PR нельзя было смержить, один раз включите защиту ветки:
**Settings → Branches → Add classic branch protection rule** → Branch name pattern `main` →
**Require status checks to pass before merging** → выберите все три задания → **Create**.
Задания появляются в списке после первого запуска CI.

## Что осталось за рамками MVP

- Онлайн-оплата: сейчас заказ создаётся со статусом «новый», оплата по факту или переводом.
- Уведомления покупателю о смене статуса заказа (email / SMS); менеджеру новые заказы уже
  приходят в Telegram.
- Автоматическая модерация оптовых заявок (проверка документов).
- SEO: сейчас страницы каталога рендерятся на клиенте, потому что цены зависят от роли.
  Для индексации можно добавить SSR гостевой версии и slug-URL товаров.
- Поиск с опечатками (pg_trgm), избранное, отзывы.
- Склад: печать своих этикеток со штрихкодами, учёт кодов маркировки DataMatrix, отмена
  проведённой приёмки (сейчас ошибку исправляют инвентаризацией), несколько складов.
- Токены сейчас хранятся в `localStorage`. Для продакшена стоит перенести refresh-токен в
  httpOnly-cookie и добавить Content-Security-Policy.
