# Kyko Parfums — маркетплейс парфюмерии и косметики

MVP веб-платформы для розничной и оптовой продажи парфюмерии: каталог с нотами и
олфактивными группами, три уровня цен (розница / опт / крупный опт), корзина и заказы
без онлайн-оплаты, личный кабинет и админ-панель с импортом каталога из Excel.

| Слой | Технологии |
|---|---|
| Backend | Python 3.11, FastAPI, SQLAlchemy 2, Alembic, PostgreSQL 16, JWT (PyJWT), bcrypt |
| Frontend | Next.js 16 (App Router, Turbopack), React 19, Tailwind CSS 4, TypeScript |
| Админка | Защищённый раздел `/admin` на том же фронтенде |
| Инфраструктура | Docker Compose (db + backend + frontend) |

## Быстрый старт (Docker)

```bash
cp .env.example .env            # задайте JWT_SECRET
docker compose up -d --build
docker compose exec backend python -m app.cli create-admin admin@example.com 'сложный-пароль'
docker compose exec backend python -m app.cli seed-demo           # демо-товары и пользователи (необязательно)
```

- Сайт: http://localhost:3000, админка: http://localhost:3000/admin
- API и Swagger: http://localhost:8000/docs

Миграции применяются автоматически при старте backend-контейнера.

## Деплой в облако (Render, бесплатный тариф)

В корне лежат `Dockerfile` (сайт и API в одном контейнере) и `render.yaml` (Blueprint:
веб-сервис + бесплатный PostgreSQL).

1. Зарегистрируйтесь на https://render.com через GitHub и дайте доступ к репозиторию.
2. **New → Blueprint** → выберите репозиторий и ветку с `render.yaml`.
3. Render спросит `ADMIN_EMAIL` и `ADMIN_PASSWORD` (не короче 8 символов): это будет ваш вход
   в админку. `JWT_SECRET` сгенерируется сам, `DATABASE_URL` подставится из базы.
4. **Apply** — первая сборка идёт ~5–10 минут. Сайт откроется по адресу вида
   `https://kyko-parfums.onrender.com`.

При первом старте применяются миграции, создаётся админ и (при `SEED_DEMO=true`)
заливаются демо-товары и демо-аккаунты. При перезапусках ничего не дублируется.

Ограничения бесплатного тарифа: сервис засыпает через ~15 минут простоя, первый запрос после
сна идёт ~1 минуту; бесплатная база Render живёт ограниченный срок; загруженные фото хранятся
на диске контейнера и пропадают при новом деплое (для продакшена — S3 / платный диск).
Демо-аккаунты с паролем `password123` публичны — перед реальным запуском удалите их
или заблокируйте в админке.

Сайт на Render стоит собирать из ветки `main`: тогда на прод попадает только то, что смержено.

### Миграции и откат неудачного деплоя

При старте контейнер выполняет `python -m app.cli migrate`, а не голый `alembic upgrade head`.
Бывает, что новая версия уже обновила базу, но её деплой упал, и Render оставил работать
предыдущую сборку. Предыдущая сборка не знает новой ревизии базы, и голый `alembic upgrade head`
падает при каждом старте.

Поэтому каждая миграция обязана объявить `backward_compatible`: работает ли код, написанный до
неё, на схеме после неё.

- `True`: новые таблицы, колонки, которые могут быть пустыми или имеют значение по умолчанию
  (`server_default`), ослабленные ограничения.
- `False`: колонка NOT NULL без значения по умолчанию, удаление или переименование, более
  строгие ограничения.

Флаг говорит только о схеме: он страхует упавший деплой, когда новый код ещё ничего не записал.
Откатывать сайт на старую сборку после того, как новая поработала, нужно осторожно: новая могла
записать данные, которых старая не знает (например, новые причины движения склада).

После каждого прогона Alembic база запоминает в таблице `schema_compat`, код какой ревизии она
требует как минимум. Если база новее кода, `migrate` запускает приложение, только когда код не
старше этого минимума. Иначе контейнер не стартует и пишет в лог, какую версию выкатить.
Миграция без флага не применится, а тесты упадут.

Ломающие изменения лучше делать в два релиза: сначала добавить (колонку, которая может быть
пустой, или значение по умолчанию), потом, отдельной миграцией, ужесточить или удалить.

## Локальная разработка

Нужны Python 3.11+, Node.js 20.9+ и PostgreSQL.

```bash
# БД
createuser -s kyko && createdb -O kyko kyko && createdb -O kyko kyko_test

# Backend (http://localhost:8000)
cd backend
python -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env
alembic upgrade head
python -m app.cli create-admin admin@example.com admin12345
python -m app.cli seed-demo
uvicorn app.main:app --reload

# Frontend (http://localhost:3000) — /api и /media проксируются на backend
cd frontend
npm install
npm run dev
```

Демо-аккаунты после `seed-demo` (пароль `password123`):

| Email | Роль |
|---|---|
| retail@example.com | Розница |
| wholesale@example.com | Опт |
| bulk@example.com | Крупный опт |

Оптовая цена зависит только от роли покупателя: пороги по сумме заказа выключены (равны 0).

## Роли и цены

| Роль | Что видит | Какую цену может получить |
|---|---|---|
| Гость | Каталог, розничные цены | Розничную (для заказа нужен вход) |
| Розница (`retail`) | Розничные цены | Розничную |
| Опт (`wholesale`) | Розница + опт | Оптовую |
| Крупный опт (`bulk_wholesale`) | Все три цены | Крупнооптовую |
| Админ (`admin`) | Всё + админ-панель | — |

Роли опт/крупный опт назначает администратор вручную. Покупатель отправляет заявку из
личного кабинета: розница просит опт (указывает компанию и телефон), опт просит крупный опт
(с комментарием об объёмах). Заявки с комментарием подсвечиваются в «Пользователях». Когда
админ повышает роль, заявка закрывается, а новые цены действуют сразу, даже для уже выданных
токенов.

**Кто какие цены видит.** Розничные покупатели и гости оптовых цен не видят никогда. Иначе
покупатели ваших оптовиков-перепродавцов увидели бы их закупочную цену. Вместо цен в каталоге
и на карточке товара показывается блок «Для магазинов и салонов» с кнопкой заявки. Оптовикам
показывается «ваша следующая цена» — цена крупного опта с условиями и кнопкой «Запросить
крупный опт», а в корзине — сколько стоил бы заказ на крупном опте. Этот тизер включается и
выключается в «Цены и скидки», там же пишутся условия перехода. Колонка цен крупного опта
по-прежнему видна только крупным оптовикам.

У каждого объёма товара (30/50/100 мл…) свои остаток и три цены. Если оптовая или
крупнооптовая цена не заполнена, берётся цена уровнем выше (крупный опт → опт → розница).

### Порог перехода на опт

Решение: **опт определяется ролью**, независимо от суммы заказа, поэтому пороги равны 0.
Если когда-нибудь понадобится минимальная сумма или количество для опта, это включается в
админке («Цены и скидки») без релиза. Поддержаны два режима:

- **По сумме заказа** (`order_total`, режим по умолчанию). Уровень цены выбирается один раз
  для всего заказа: лучший доступный роли уровень, у которого сумма заказа (посчитанная по
  ценам этого уровня) не меньше порога. Пример: опт от 150 000 ₸, крупный опт от 500 000 ₸.
- **По количеству единиц** (`item_quantity`). Уровень выбирается для каждой позиции: оптовая
  цена действует, если одного объёма в заказе не меньше N штук.

Если порог не достигнут, позиция считается по рознице, и оптовик всё равно может оформить
заказ. Корзина подсказывает, сколько не хватает («добавьте ещё на 88 800 ₸» / «ещё 2 шт.»).

Цены всегда считает сервер (`POST /api/cart/quote`, `POST /api/orders`). Корзина хранится в
браузере, и при оформлении цены пересчитываются заново. В заказ записываются применённая цена,
её уровень и снимок товара, поэтому история заказов не меняется при правке каталога.

## Продажи в магазине (оффлайн) и журнал склада

Покупки в физическом магазине админ проводит в разделе **«Продажа в магазине»** (`/admin/pos`).
Экран удобен с телефона или планшета у кассы.

- Товар ищется по названию, бренду или артикулу. Сканер штрихкодов работает как клавиатура:
  сканируете код, и позиция сразу попадает в чек (точное совпадение артикула).
- Покупатель необязателен. Можно найти клиента по телефону, email или имени: тогда подставится
  его уровень цены (опт / крупный опт), а продажа попадёт в его историю заказов. Для анонимного
  покупателя можно записать имя и телефон.
- Уровень цены выбирается автоматически или вручную. Скидка задаётся на позицию или на весь
  чек, но не больше лимита из «Цены и скидки» (по умолчанию 10%).
- Способ оплаты: наличные, карта, Kaspi / перевод, другое.
- Продажа сохраняется как заказ с каналом «Магазин» и статусом «Доставлен», остатки списываются
  сразу. Если товара на складе меньше, чем в чеке, провести продажу нельзя.
- Возврат, в том числе частичный: откройте продажу и нажмите «Оформить возврат» (см. ниже).
- В «Заказах и продажах» есть фильтр «Сайт / Магазин», на дашборде — выручка по каналам и
  продажи в магазине за сегодня. Фискальный чек система не печатает, его пробивают на кассе.

Каждое изменение остатка записывается в **журнал склада** (таблица `stock_movements`): заказ на
сайте, продажа в магазине, отмена или возврат, ручная правка в админке (с причиной, например
«приход от поставщика»), импорт Excel. Журнал виден в карточке товара в разделе
«Движение склада». В нём видно, когда, на сколько, почему и кем изменён остаток.

## Изменение заказа и возвраты

**До выдачи** (статус «Новый» или «В обработке») админ может нажать «Изменить состав», уменьшить
количество или убрать позиции, например если товара нет в наличии. Снятый товар возвращается
на склад, сумма пересчитывается, цены оставшихся позиций не меняются. Покупатель видит в
кабинете тот же заказ: убранные позиции зачёркнуты, в истории указана причина. Убрать все
позиции нельзя — такой заказ отменяется целиком.

**После выдачи** (статус «Доставлен», в том числе все продажи в магазине) оформляется
возврат: какие позиции и сколько штук вернули, способ возврата денег и причина. По каждой
позиции выбирается «на склад» или «брак — списать». Сумма считается по цене, за которую товар
купили (с учётом скидки). Возвратов по заказу может быть несколько, пока не вернут всё.
Выручка на дашборде показывается за вычетом возвратов.

У каждого заказа есть история (оформлен, смена статуса, изменения состава, возвраты). Её
видят и админ, и покупатель.

## Склад: сканер, приёмка, инвентаризация, сборка

**Сканер.** Подходит любой USB- или Bluetooth-сканер штрихкодов в режиме клавиатуры (HID) с Enter
после кода — так они настроены по умолчанию, драйверы не нужны. Каждое нажатие курка — одна
штука. Курсор может стоять где угодно: сайт отличает сканер от человека по скорости (сканер
печатает символы с промежутком в несколько миллисекунд) и отправляет код в сканер страницы, а
поле, куда он случайно напечатался (количество, цена, имя покупателя), возвращает как было.
Раскладка тоже не важна: при таком вводе буквы берутся по физическим клавишам, а код с кириллицей,
набранный в поле сканера, переводится в латиницу по расположению клавиш («ФИС12345» →
«ABC12345»).

На телефоне главная кнопка — «Сканировать камерой», поле ниже — для ввода кода руками (или для
Bluetooth-сканера); на компьютере наоборот. Камере нужен https. Распознавание: встроенный в
браузер детектор, где он есть (Chrome на Android), иначе ZXing (iPhone).

Камера работает по правилу «один скан — одно действие»:

1. читается только штрихкод внутри рамки, соседние коробки на полке не мешают;
2. как только код прочитан, кадр замирает, телефон вибрирует и видно «Код … прочитан · ищем
   товар…» — держать камеру дальше не нужно;
3. появляется карточка: товар, количество с кнопками −/+ и «Отменить этот скан». Больше ничего
   не считывается, пока не нажата «Следующий товар» (или тап по кадру). Сразу после этого тот
   же код игнорируется, пока не уйдёт из рамки, — коробка, оставшаяся перед камерой, не
   посчитается дважды. Несколько одинаковых коробок быстрее добавить кнопкой «+».

После скана звучит сигнал: короткий высокий — принято, длинный низкий — ошибка. Карточка
последнего скана с −/+ и отменой остаётся и под полем ввода (для ручного сканера). Незнакомый
код предлагает «Привязать к товару». Если телефон умеет, в камере есть кнопка «Фонарик».

**Штрихкоды** хранятся у объёма, их может быть несколько (коробка, тестер, разные поставщики).
Добавить можно в карточке товара, при импорте (колонка «Штрихкод», несколько кодов через
запятую) или прямо при приёмке: незнакомый код предлагается привязать к товару. Старые
штрихкоды, импортированные в «Артикул», тоже находятся. UPC-A (12 цифр) и EAN-13 с ведущим нулём
считаются одним кодом.

**Приёмка** (`/admin/receipts`) — приходная накладная: поставщик, № накладной, товары и
закупочные цены. Каждый скан добавляет 1 шт.; цена подставляется из прошлой приёмки. Пока
документ — черновик, остатки не меняются. «Провести» добавляет товар на склад (в журнале
причина «Приёмка» со ссылкой на документ) и пересчитывает **себестоимость** объёма по
скользящей средней: `(остаток × старая себестоимость + пришло × цена) / (остаток + пришло)`.
Если прежняя себестоимость неизвестна, берётся цена прихода. Проведённый документ не меняется.

**Инвентаризация** (`/admin/inventory`) — пересчёт полки или всего склада сканером. Видно,
сколько в системе и сколько посчитано. При проведении остатки посчитанных объёмов становятся
равны посчитанному, расхождение пишется в журнал (причина «Инвентаризация»). Не посчитанные
объёмы не меняются: товар, которого нет на полке, добавьте через поиск с количеством 0.

**Сборка онлайн-заказа** — кнопка «Собрать заказ» у заказа в статусе «Новый» или «В обработке».
Сканируйте товары: система отмечает собранное и предупреждает о другом объёме, лишней штуке или
товаре не из заказа. Когда всё собрано — кнопка «Отметить „Отправлен“». Склад при сборке не
меняется: он списан при оформлении. Прогресс сборки сохраняется при перезагрузке вкладки.

**Касса** принимает скан сразу: товар по штрихкоду добавляется в чек.

**Маржа.** Каждая продажа запоминает себестоимость единицы на момент продажи. На дашборде:
валовая прибыль и маржа по продажам с известной себестоимостью (с учётом возвратов), стоимость
склада по себестоимости и число объёмов в наличии без себестоимости. Себестоимость можно задать
и вручную в карточке товара, а при импорте — колонкой «Себестоимость».

## Импорт каталога из Excel

Файл кладётся в `data/` (папка в `.gitignore`), затем:

```bash
cd backend
python -m app.cli import-catalog ../data/catalog.xlsx --dry-run   # отчёт без записи
python -m app.cli import-catalog ../data/catalog.xlsx
python -m app.cli template ../data/template.xlsx                  # пустой шаблон
```

Или через админку: «Импорт Excel» (там же скачивается шаблон).

- Форматы: `.xlsx` и `.csv` (UTF-8 или Windows-1251, разделитель `,` `;` или табуляция).
- Строка заголовков ищется среди первых 15 строк, колонки распознаются по названию
  (рус./англ.): Бренд, Название, Тип, Категория / Олфактивная группа, Пол, Стойкость,
  Верхние ноты, Ноты сердца, Базовые ноты, Описание, Фото, Объём, Цена / Розница, Опт,
  Крупный опт, Остаток, Артикул. Нераспознанные колонки перечисляются в отчёте.
- Одна строка — один товар. Если в строке заполнены объём и розничная цена, создаётся ещё и
  вариант. Строки с одинаковыми брендом, названием и типом дают несколько объёмов одного товара.
- Значения нормализуются: «Женский / жен. / women» → female, «Парфюмерная вода /
  Eau de Parfum» → EDP, цены вида «45 000 ₸» или «45,5» разбираются как числа.
- Повторный импорт идемпотентен: товары сопоставляются по (бренд, название, тип), а пустые
  ячейки не затирают уже заполненные данные. Так можно сначала залить базу из 932 позиций без
  цен, а позже догрузить цены и объёмы тем же или отдельным файлом.
- Ошибочные строки пропускаются и попадают в отчёт с номером строки Excel.

Товары без объёмов и цен видны в каталоге с пометкой «Цена по запросу». В админке для них
есть фильтр «Без цен/объёмов», а на дашборде — счётчик.

### Фото флаконов

Фото поставщиков лежат в `frontend/public/bottles` и отдаются самим сайтом, поэтому переживают
передеплой. Флаконы на них сняты по-разному: где-то занимают весь кадр, где-то маленькие
посреди пустого фона. Скрипт приводит их к одному виду: квадрат 600×600, бутылка по центру,
её длинная сторона занимает 86 % кадра, фон белый.

```bash
cd backend
pip install Pillow
python scripts/normalize_photos.py ../frontend/public/bottles --dry-run   # отчёт без изменений
python scripts/normalize_photos.py ../frontend/public/bottles
```

- Светлый фон становится чисто белым. Чисто чёрный фон — это обычно потерянная прозрачность
  (PNG, сохранённый в JPEG): он заливается белым от краёв, тёмные детали флакона не трогаются.
- Фото с неоднородным фоном (градиент, интерьер) не меняются, скрипт перечисляет их в конце.
- Имена файлов не меняются, ссылки на фото в товарах остаются рабочими. Обработанные файлы
  помечаются, повторный запуск их пропускает. Запускайте после добавления новых фото.

## Восстановление пароля

`POST /api/auth/forgot-password` отправляет письмо со ссылкой `/reset-password?token=…`
(одноразовый токен, живёт 60 минут, в БД хранится только его sha256). Если SMTP не настроен
(`SMTP_HOST` пустой), ссылка пишется в лог backend'а. Это удобно для разработки. Смена или
сброс пароля отзывает все refresh-токены пользователя.

Защита от перебора: после 10 неверных паролей подряд вход в этот аккаунт закрыт на 15 минут
(ответ 429 с `Retry-After`, даже при верном пароле). Писем для сброса — не больше 3 в час на
адрес; сверх лимита ответ тот же, письмо не уходит. Счётчики живут в памяти процесса и
сбрасываются при перезапуске.

### Схема БД

`users`, `brands`, `products`, `product_variants`, `orders`, `order_items` — как в ТЗ. Сверх ТЗ
добавлено:

- `users`: `full_name`, `phone`, `company_name`, `wholesale_requested`, `is_active`,
  `token_version` (отзыв refresh-токенов);
- `products`: `image_url` (главное фото), `is_active`;
- `product_variants`: `sku`, `is_active`, `cost_price` (средняя себестоимость), уникальность
  (товар, объём), CHECK на цены и остатки; `variant_barcodes` — штрихкоды объёма;
- `orders`: контакты и адрес доставки, `customer_role` на момент заказа, `admin_note`;
- `order_items`: `price_tier`, `cost_price` на момент продажи и снимок товара (бренд, название,
  объём);
- `stock_movements` — журнал склада; `stock_receipts` / `stock_counts` (+ строки) — приёмки и
  инвентаризации;
- `pricing_settings` — режим и пороги опта;
- `password_reset_tokens`.

Остаток списывается при оформлении заказа под блокировкой строк (`SELECT … FOR UPDATE`), так
что параллельные заказы не уводят склад в минус. При отмене заказа товар возвращается на склад.
Переходы статусов: новый → в обработке → отправлен → доставлен; отменить можно до доставки.
Покупатель сам может отменить только новый заказ.

## Что осталось за рамками MVP

- Онлайн-оплата: сейчас заказ создаётся со статусом «новый», оплата по факту или переводом.
- Уведомления о заказах (email / Telegram менеджеру).
- Автоматическая модерация оптовых заявок (проверка документов).
- SEO: сейчас страницы каталога рендерятся на клиенте, потому что цены зависят от роли.
  Для индексации можно добавить SSR гостевой версии и slug-URL товаров.
- Хранение фото в S3 / CDN (сейчас локальная папка `media`, в Docker — volume).
- Поиск с опечатками (pg_trgm), избранное, отзывы.
- Склад: печать своих этикеток со штрихкодами, учёт кодов маркировки DataMatrix, отмена
  проведённой приёмки (сейчас ошибку исправляют инвентаризацией), несколько складов.
- Токены сейчас хранятся в `localStorage`. Для продакшена стоит перенести refresh-токен в
  httpOnly-cookie и добавить Content-Security-Policy.
